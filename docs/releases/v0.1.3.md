# Endure v0.1.3

Protocol key `2044` pools identical forecasts in emission weights. The economics
remain experimental, and mainnet serving still needs the explicit operator
acknowledgement.

- Package/API version `0.1.3`, release tag `v0.1.3`.
- Protocol key `2044` replaces `2043`. **Miners and validators must upgrade
  together**: a key-`2043` peer is rejected with `VERSION_MISMATCH`.
- Images: `ghcr.io/endure-network/endure-subnet-validator` and
  `ghcr.io/endure-network/endure-subnet-miner`, Linux/amd64, on `:prod` and
  `:v0.1.3`. Deploy by digest.
- No chain-parameter change: SN30's `weights_version` (`2040`) accepts key
  `2044`.
- No schema migration and no new dependency.

## What changed

- **Identical-forecast pooling.** Each hotkey joins the oldest group of hotkeys
  that revealed its values in one of the five newest revealed rounds, and a
  pool weighs what its best member would alone, so `k` copies in one pool split
  one miner's weight. A new copy joins its pool at the latest once the round it
  first matched in is the window's oldest. Forecasts that differ in any value
  are scored and paid as before. See
  [identical forecasts](../mining.md#identical-forecasts-share-one-payout).
- **One rounding per pool.** The vote rounds each pool to whole u16 units once.
  Ties follow the hash of a finalized mainnet block read from the market-data
  archive, so every validator with the same window agrees.
- **Startup checks.** Every validator that reads live mainnet data, testnet
  included, must pass the
  [archive preflight](../running_on_mainnet.md#release-pinned-consensus-policy-key-2042),
  and `--endure.health_tick_max_duration_seconds` must exceed
  `--endure.resolution_budget_seconds` plus 600 seconds; the defaults pass. A
  validator restarted while its archive cannot show a tie seed abstains until
  it reads one; see
  [identical forecasts](../running_on_mainnet.md#identical-forecasts).
- **`/miners`** reports the pooled `weight_share` and each hotkey's `pool_size`.

Scores, EMAs, consensus weighting and the
[owner burn rate](../running_on_mainnet.md#owner-burn-rate) are unchanged. The
[CHANGELOG](../../CHANGELOG.md) lists the changes.

## Operator upgrade

Follow the [coordinated cutover](../running_on_mainnet.md#coordinated-cutover):

1. Upgrade miners and validators together between 00:00 and 11:00 UTC, before
   the day's commit window opens. The tag moves `:prod`, so a validator that
   tracks that channel gets key `2044` at its next pull.
2. Back up the database, and keep the `v0.1.2` image references.
3. Check that `--endure.market_data_endpoint` reaches a mainnet archive node,
   and that custom budgets keep the 600-second margin.
4. Run exactly one weight writer per hotkey. The first vote lands roughly 300
   blocks after start.
5. Check that `/health` reports key `2044` and the expected source and content
   revisions, and that `/miners` reports `pool_size` once the validator has read
   a tie seed.

The owner burn rate is unchanged, so the owner takes no action.

## Release decision

On 2026-10-16 the owner scoped an exception to the seven-day soak:

- private qualification of the release tree: `make verify`, and a local devnet
  run in which two miners revealing identical values share one miner's
  incentive, with a restart that rebuilds the pools. The staging commit the tag
  promotes must carry that tree, or the devnet run is repeated on it;
- a testnet soak of at most about 24 hours on that staging commit, with these
  checkpoints: `/health` reports key `2044` and the expected revisions; a
  confirmed key-`2044` weight submission; a deliberate restart that comes back
  to another confirmed submission; and, added on 2026-10-19, one full round:
  the first testnet round run on key `2044` from its commit window to its
  reveal close joins the pool window, and a confirmed submission is computed
  from that window;
- the `:prod` promotion between 00:00 and 11:00 UTC, with the team's validator
  as the mainnet canary. Operators are asked to upgrade once it has a confirmed
  key-`2044` submission and its `/miners` reports `pool_size`.

CI, localnet qualification and published images on that staging commit remain
required. The GitHub release records each checkpoint's outcome. The
[economic limitations](../economic-limitations.md) remain disclosed: pooling
prices exact replication only.

## Publication and rollback

The production workflow retags the qualified staging commit's `sha-<commit>`
images as `:prod` and `:v0.1.3` without rebuilding. Before the canary, their
digests are checked against the ones the staging run recorded, and the GitHub
release records them. The testnet soak runs a Coolify build of the same source,
so the published images are checked by content revision, not by digest.

Rollback is an image swap that keeps the database: return miners and validators
to the key-`2043` `v0.1.2` images together, between 00:00 and 11:00 UTC, as in
the [operator rollback procedure](../deploy/operator-node.md#rollback). Keep the
pre-upgrade backup for corruption only: restoring it discards everything written
since the upgrade.
