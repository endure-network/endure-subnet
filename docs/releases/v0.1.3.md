# Endure v0.1.3

This release pools identical forecasts in emission weights under protocol key `2044`. The economics remain experimental, and mainnet serving still needs the explicit operator acknowledgement.

- Package/API version: `0.1.3`
- Release tag: `v0.1.3`
- Protocol key: `2044`. It replaces `2043`, and **miners and validators must upgrade together**. A key-`2043` peer is rejected with `VERSION_MISMATCH`.
- Images: `ghcr.io/endure-network/endure-subnet-validator` and `ghcr.io/endure-network/endure-subnet-miner`, Linux/amd64.
- Channels: `:testnet` for qualified staging candidates; `:prod` and `:v0.1.3` for this release. Deploy by digest to pin exact image bytes.
- Chain parameters: **no `weights_version` change.** SN30's `weights_version` is `2040`, and Subtensor accepts any `version_key` at or above it, so key-`2044` submissions are accepted as-is. Scored votes still need chain `min_allowed_weights` of `1` and a `max_weight_limit` of `1` (u16 `65535`), which SN30 already has.

## What changed

See the [CHANGELOG](../../CHANGELOG.md) for the itemised list.

- **Identical-forecast pooling:**
  - Each scored miner is assigned to the oldest group of miners that revealed identical values with it in one of the five newest revealed rounds.
  - The members of a group together weigh what its best member would alone, so `k` identical submissions split one miner's weight. Pools never overlap.
  - Only submitted values are compared. Forecasts that differ in any value are scored and paid as before.
  - Scores, EMAs, consensus weighting and the [owner burn rate](../running_on_mainnet.md#owner-burn-rate) are unchanged; the burn applies to the pooled vector.
- **Rounding and tie order:**
  - The vote rounds each pool to whole u16 units once, as it would one hotkey.
  - Equal remainders within a pool are ordered by the hash of the first finalized mainnet block stamped at least one minute after the newest round's reveal close. Every validator with the same window draws the same order.
  - A round joins the window once that block is final, a minute or two after its reveals close.
- **Archive and startup:**
  - Validators read the tie-seed block from their market-data archive (`--endure.market_data_endpoint`). Every validator that reads live mainnet data, testnet included, must pass the [archive preflight](../running_on_mainnet.md#release-pinned-consensus-policy-key-2042) to start.
  - Such a validator also refuses to start unless `--endure.health_tick_max_duration_seconds` exceeds `--endure.resolution_budget_seconds` plus 600 seconds, room for two seed reads. The defaults, 1800 and 600, pass.
  - While the archive cannot show the newest seed, a running validator votes with the newest window whose seed it has read. A validator that restarts while its archive answers but cannot yet show a seed starts, abstains with `score_state_unavailable`, and its `/miners` answers 503, until it reads one. If the archive is down outright, the preflight stops it from starting.
- **`/miners`** reports the validator's newest pooled `weight_share` and each hotkey's `pool_size`.
- **Miners:** hotkeys that reveal exactly the same values share one payout. See [identical forecasts](../mining.md#identical-forecasts-share-one-payout).

This release adds no schema migration and no new dependency. Key `2044` has its own protocol digest; the package version bump to `0.1.3` leaves it unchanged.

## Operator upgrade

Follow the [coordinated cutover](../running_on_mainnet.md#coordinated-cutover). In short:

1. **Cut over between 00:00 and 11:00 UTC,** before the day's commit window opens, so that the day's round runs on key `2044` throughout. A key-`2044` validator rejects key-`2043` submissions, so miners upgrade in the same window.
2. **Keep the owner burn rate published.** The rate is unchanged, so the owner takes no action for this release.
3. **Back up the database** with a consistent SQLite backup, and keep the previous key-`2043` image references.
4. **Check the archive and budgets.** The validator's `--endure.market_data_endpoint` must reach a mainnet archive node, and custom `--endure.resolution_budget_seconds` values must stay more than 600 seconds below `--endure.health_tick_max_duration_seconds`.
5. **Switch weight writers without overlap**, as for `v0.1.2`. Run exactly one writer per hotkey. The first vote lands after the startup fence and epoch pacing, roughly 300 blocks after start.
6. **Monitor `/health` and `/miners`:**
   - `/health` reports protocol key `2044` and the expected source and content revisions;
   - `emission_mode`, `emission_reason`, `emission_burn_bps` and `last_confirmed_weights_at` work as before;
   - `/miners` reports `pool_size` once the validator has read a tie seed.

## Owner soak decision — 2026-10-16

The owner decided not to wait for the default seven-day unchanged-revision soak for this release. This is a scoped exception to that rule, in three parts:

- **Private qualification first,** on the release's source tree before it is public: `make verify`, and a local devnet run in which two miners revealing identical values share one miner's on-chain incentive, with a restart that rebuilds the pools. The staging commit that the tag promotes must carry the same tree; if it does not, the devnet run is repeated on that commit.
- **Then a targeted soak of at most about 24 hours** on testnet, on the staging commit whose published `sha-<commit>` images the `v0.1.3` tag promotes. Its checkpoints are:
  - a confirmed key-`2044` weight submission on testnet;
  - a deliberate restart after that submission, which comes back to another confirmed key-`2044` weight submission;
  - `/health` reporting key `2044` and the expected source and content revisions;
  - one full round on key `2044`: the first testnet round that runs on it from its commit window to its reveal close joins the pool window, and a confirmed key-`2044` weight submission is computed from that window. The owner added this checkpoint on 2026-10-19.
- **Then the `:prod` promotion between 00:00 and 11:00 UTC.** The tag moves `:prod`, so validators that track that channel may upgrade on promotion. The team's own validator cuts over first, as the mainnet canary, and operators are asked to upgrade once it has a confirmed key-`2044` weight submission and its `/miners` reports `pool_size`.

CI, localnet qualification and published images on the exact final staging commit remain required. This document records the decision and its criteria only. The GitHub release records the outcome of each checkpoint, and of the canary once it is known.

The economic and independent-validator limitations in [economic limitations](../economic-limitations.md) remain disclosed and are not represented as resolved. Pooling prices exact replication only; it does not bound the number of identities one operator runs.

## Publication and rollback

Promote `develop` to `staging`, then `staging` to `main`, using merge commits. Tag the qualified staging commit reachable from `main`, because its `sha-<commit>` images are the inputs to production publication. The production workflow retags the current `sha-<commit>` images as `:prod` and `:v0.1.3` without rebuilding. Before the canary, check that both digests equal the ones the qualified staging run recorded, which `:testnet` also carries, and record them in the GitHub release.

Coolify builds separately from the same source. Source identity and runtime content checks do not prove that its image digest equals the published image digest, and this release does not claim that equivalence.

This release adds no schema migration, so rolling back is an image swap that keeps the database. Return *both* miners and validators to the key-`2043` `v0.1.2` images together, between 00:00 and 11:00 UTC as for the cutover, following the [operator rollback procedure](../deploy/operator-node.md#rollback). Keep the pre-upgrade backup for corruption only: restoring it would discard every round, score and weight record written since the upgrade.
