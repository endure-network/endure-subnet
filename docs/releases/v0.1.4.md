# Endure v0.1.4

Protocol key `2045` keeps validators voting through archive throttling and
outages, and weights each 30-day EMA by its maturity in the blended score. The
economics remain experimental, and mainnet serving still needs the explicit
operator acknowledgement.

- Package/API version `0.1.4`, release tag `v0.1.4`.
- Protocol key `2045` replaces `2044`. **Miners and validators must upgrade
  together**: a key-`2044` peer is rejected with `VERSION_MISMATCH`.
- Images: `ghcr.io/endure-network/endure-subnet-validator` and
  `ghcr.io/endure-network/endure-subnet-miner`, Linux/amd64, on `:prod` and
  `:v0.1.4`. Deploy by digest.
- No chain-parameter change: SN30's `weights_version` (`2040`) accepts key
  `2045`.
- Schema migration `0016` stores pool tie seeds; the validator applies it at
  startup. No new dependency.

## What changed

- **Throttled archives.** A validator whose archive only rate-limits it at
  startup starts with `/health` `runtime.archive_check` set to `unverified` and
  re-checks hourly; a wrong chain or missing history still refuses startup or,
  found by a re-check, stops the validator. Any rate-limit answer pauses all
  archive reads for 60 seconds, and a throttled timestamp read is retried
  instead of read as zero. See the
  [archive preflight](../running_on_mainnet.md#release-pinned-consensus-policy-key-2042).
- **Stored tie seeds.** Each round's pool tie seed is stored once read, so a
  restarted validator votes without reading the archive, and during an archive
  outage running and restarted validators vote alike; see
  [identical forecasts](../running_on_mainnet.md#identical-forecasts).
- **Faster boundary searches.** Timestamp-to-block searches take about 4 archive
  reads instead of 25 and return the same blocks.
- **Horizon-maturity blend.** The blended score counts each 30-day EMA by its
  maturity, so a young 30-day record no longer reads as poor accuracy. For each
  netuid and output, up to 20% of the 5-day score is held back until the
  30-day record matures. After sharpening, a new hotkey earns about half what an
  equally accurate miner with a full record earns; the gap closes as its 30-day
  rounds resolve, from about day 30 to day 60. See
  [eligibility and the earnings timeline](../mining.md#eligibility-and-the-earnings-timeline).
- **Tick budget.** `--endure.health_tick_max_duration_seconds` must exceed
  `--endure.resolution_budget_seconds` plus 780 seconds, up from 600, to leave
  room for an archive re-check; the defaults pass.
- **Operator-node miners** read `MINER_MARKET_DATA_ENDPOINT`, which defaults to
  the public lite node. A miner that took a private endpoint from
  `MARKET_DATA_ENDPOINT` keeps it only if you set the new variable.

Pooling and the [owner burn rate](../running_on_mainnet.md#owner-burn-rate) are
unchanged; pay, `/miners` and consensus weighting all use the new blended score.
The [CHANGELOG](../../CHANGELOG.md) lists the changes.

## Blend replay

Replayed on the public validator APIs as of 2026-11-09 07:00 UTC, hotkeys with
no resolved 30-day round fall from 36.2% to 13.0% of miner weight on UID 48,
from 29.7% to 11.0% on UID 55 and from 20.8% to 9.4% on testnet, and the best
of them drops from rank 1 to 33 on both mainnet validators. Published medians
barely move: over UID 55's rounds from 10-29 to 11-03, the medians' mean score
against realized 5-day outcomes stays at 0.93889 across 360 cells (10 better,
9 worse), and on rounds with resolved 30-day outcomes 7 of 720 medians change
on UID 55 and 1 of 240 on UID 48, with mean scores unchanged to four decimals.
UID 48's medians from round 11-06 move more (about 50 of 120 cells per round,
about 90 bps on average); their 5-day outcomes first resolve on 11-12.

## Operator upgrade

Follow the [coordinated cutover](../running_on_mainnet.md#coordinated-cutover):

1. Upgrade miners and validators together between 00:00 and 11:00 UTC, before
   the day's commit window opens. The tag moves `:prod`, so a validator that
   tracks that channel gets key `2045` at its next pull.
2. Back up the database, and keep the `v0.1.3` image references. The validator
   applies migration `0016` when it starts, so a rollback needs this backup.
3. Point `--endure.market_data_endpoint` at your own keyed mainnet archive; the
   public archive throttles validator resolution. Custom budgets must keep the
   780-second margin.
4. On the [operator-node template](../deploy/operator-node.md), set
   `MINER_MARKET_DATA_ENDPOINT` if your miner should keep a private endpoint.
5. Run exactly one weight writer per hotkey. The first vote lands roughly 300
   blocks after start; until the validator reads its first tie seed, it
   abstains with `score_state_unavailable` and `/miners` answers 503.
6. Check that `/health` reports key `2045`, the expected source and content
   revisions, and `runtime.archive_check` `passed`.

The owner burn rate is unchanged, so the owner takes no action.

## Release decision

The default seven-day [testnet soak gate](../running_on_staging.md#testnet-soak-gate)
applies, with no exception. Staging deploys the release commit between 00:00
and 11:00 UTC on 2026-11-12. Once the gate passes, the `:prod` promotion and
the cutover follow between 00:00 and 11:00 UTC, with the team's validator as
the mainnet canary. Operators are asked to upgrade once it has a confirmed
key-`2045` submission. CI, localnet qualification and published images on that
staging commit remain required, and the GitHub release records the gate's
outcome. The [economic limitations](../economic-limitations.md) remain accepted
and disclosed.

## Publication and rollback

The production workflow retags the qualified staging commit's `sha-<commit>`
images as `:prod` and `:v0.1.4` without rebuilding. Before the canary, their
digests are checked against the ones the staging run recorded, and the GitHub
release records them. The testnet soak runs a Coolify build of the same source,
so the published images are checked by content revision, not by digest.

Rollback returns miners and validators to the key-`2044` `v0.1.3` images
together, between 00:00 and 11:00 UTC. A `v0.1.3` validator refuses to start on
a database with migration `0016`, so stop both and restore the pre-upgrade
backup before starting the `v0.1.3` images, as in the
[operator rollback procedure](../deploy/operator-node.md#rollback). Restoring it
discards everything written since the upgrade.
