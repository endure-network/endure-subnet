# Endure v0.1.1

This release carries the SN30 consensus-correctness cutover and the standing owner-vote fallback under protocol key `2042`. The economics remain experimental, and mainnet serving still needs the explicit operator acknowledgement.

- Package/API version: `0.1.1`
- Release tag: `v0.1.1`
- Protocol key: `2042`. It replaces `2041`, and **miners and validators must upgrade together**. A key-`2041` peer is rejected with `VERSION_MISMATCH`.
- Images: `ghcr.io/endure-network/endure-subnet-validator` and `ghcr.io/endure-network/endure-subnet-miner`, Linux/amd64.
- Channels: `:testnet` for qualified staging candidates; `:prod` and `:v0.1.1` for this release. Deploy by digest to pin exact image bytes.
- Chain parameters: **no `weights_version` change.** SN30's `weights_version` is `2040`, and Subtensor accepts any `version_key` at or above it, so key-`2042` submissions are accepted as-is. Raising it is a later, separate owner decision, made only after every permit validator runs `2042`.

## What changed

The full change set, review history and evidence are in [#72](https://github.com/endure-network/endure-subnet/pull/72). See the [CHANGELOG](../../CHANGELOG.md) for the itemised list.

- **Consensus correctness:**
  - Reveal persistence and snapshot closure are atomic, and frozen empty snapshots stay authoritative.
  - Capped commit retries validate the key and window.
  - Every consensus decision (admission, scoring set, emission planning, the score-to-chain composition and market-data sampling) is covered by the protocol digest.
- **Owner-vote fallback:** whenever no miner has a positive score, a served Alpha Risk validator on SN30 or testnet votes for the on-chain `SubnetOwnerHotkey` instead of abstaining. Any positive score switches it back to earned weights, with no flag or restart. Unsafe owner or chain state abstains visibly on `/health`.
- **Fixed consensus settings:** on served mainnet and testnet, the miner stake floor, commit/reveal caps and epoch length are protocol values. Operator overrides are ignored with a warning, not refused.
- **Operability:**
  - Chain identity comes from the genesis hash.
  - A pre-transport mainnet archive preflight runs at startup.
  - Exits are finalization-free, and startup failures exit promptly.
  - A durable weight-emission audit records refused and failed attempts.
  - `/health` reports the emission mode and the reason for it.
  - `/live` stays responsive under `/health` load.

This release adds no schema migration and no new dependency.

## Operator upgrade

Follow the [coordinated cutover](../running_on_mainnet.md#coordinated-cutover). In short:

1. **Back up the database.** Take a consistent SQLite backup (the backup API, or a copy taken while stopped) and keep the previous key-`2041` image references.
2. **Point `MARKET_DATA_ENDPOINT` at a mainnet archive node.** The validator's pre-transport preflight refuses to start against a non-archive or pruned endpoint.
3. **Delete ignored settings.** `MIN_MINER_STAKE`/`--endure.min_miner_stake`, `EPOCH_LENGTH`/`--neuron.epoch_length` and the per-round commit/reveal caps are ignored on served networks and can be deleted. So can `--endure.fetch_delay_seconds`, `--neuron.dont_save_events`, `--neuron.events_retention_size` and `--neuron.moving_average_alpha`. Each one still supplied logs a `WARNING` at startup.
4. **Keep the axon on for an emitting validator.** `--neuron.axon_off` on mainnet is refused unless `--neuron.disable_set_weights` is also set.
5. **Switch weight writers without overlap.**
   - Stop any external weight setter *right after* it has set weights, then start the key-`2042` validator. Run exactly one writer per hotkey; never run the external setter alongside Endure.
   - The first vote lands roughly 300 blocks after start, because of the startup fence and epoch pacing.
   - Keep the old setter configured but stopped. If the validator's on-chain `last_update` has not moved within about 2 hours, stop Endure first, then restart the old setter.
6. **Monitor `/health`:**
   - `emission_mode` and `emission_reason`: `owner_vote` or `scored`, and the reasons `startup_fence`, `epoch_pacing`, `chain_rate_limit`, `confirmation_pending`;
   - `last_confirmed_weights_at`.

   With SN30's 180-block rate limit, weights land about every 2 epochs (~202 blocks).

## Owner soak decision — 2026-09-26

The owner decided not to wait for the default seven-day unchanged-revision soak for this release. This is a scoped exception to that rule.

Instead, a targeted soak of roughly 24 hours runs on the **exact release commit**: the staging commit whose published `sha-<commit>` images the `v0.1.1` tag promotes. Its checkpoints are:

- a confirmed key-`2042` weight submission on testnet;
- one full round cycle on testnet (commit, reveal, resolution and scoring);
- a restart. The redeploy that carries this version bump to staging serves as the deliberate restart check.

After that, the release is deployed first as a mainnet canary on the Endure team's own validator (SN30 UID 195), before third-party operators are asked to upgrade.

This document records the decision and its criteria only. The outcomes of each checkpoint and the canary are recorded in the GitHub release at tag time. CI and localnet qualification remain required for the selected staging commit.

The economic and independent-validator limitations in [economic limitations](../economic-limitations.md) remain disclosed and are not represented as resolved.

## Publication and rollback

Promote `develop` to `staging`, then `staging` to `main`, using merge commits. Tag the qualified staging commit reachable from `main`, because its `sha-<commit>` images are the inputs to production publication. The production workflow adds `:prod` and `:v0.1.1` to those recorded image manifests without rebuilding. Record both resulting digests in the GitHub release.

Coolify builds separately from the same source. Source identity and runtime content checks do not prove that its image digest equals the published image digest, and this release does not claim that equivalence.

This release adds no schema migration. Rolling back means returning *both* miners and validators to the key-`2041` `v0.1.0` images together, restoring the pre-upgrade database backup, and following the [operator rollback procedure](../deploy/operator-node.md#rollback). A key-`2041` validator abstains while it has no positive scores.
